# Screening export/import and shared decisions

Source checkpoint: 2026-11-07. Implemented in code; migrations 007/008 were applied and the local demo launched during authorized setup that date. **Screening workflow/HTTP/privacy/race/manual UX gates remain pending**; seed persistence and readiness are not those passes. [OpenAPI extension](screening-openapi.json); [verification](../status.md) distinguishes setup from integration evidence.

## Eligibility and commitment

Shared admin/recruiter screening, one vacancy per wizard. Only undecided applications (`received` / compatible `review_ready`) can be screened; processing/review completion is never required. Candidate/interviewer requests are denied. Session/Origin guards and fresh database scope/state/revision checks remain authoritative.

**First committed decision wins**, not first export/upload/opened wizard. Individual stage changes and CSV apply use `interviews/screening-command.ts` under application locks. Either screening outcome records actor/time/cause, increments `flow_revision` once, clears processing token/lease/retry scheduling and makes extraction/review read-only. Original results, errors, processing aggregate status, corrections and unfinished review status remain unchanged. Preselection may later progress or be rejected through ordinary recruitment; import cannot reverse screening or perform Offer/Hired.

Review PATCH also rejects writes after review completion; completing review invalidates the processing lease. Processing claim/start/pre-execution-check/save/finish and fixture binding reject closed applications. External calls admitted before a concurrent closure may still run/cost money; late writes are fenced. No live recovery/guard/default/runner changes; the [uncertain-interruption gap](../jev-safety.md#recovery-limitation) remains.

Whole-application review readiness/manual release have a separate [B1-R/B1-J contract](processing-review-api.md#optional-shared-review), requiring migration 008. Source includes explicit release UI and factual list/filter presentation; these do not gate screening. Staff application/review detail and staff lists include `processingClosed` for release/completion/screening; candidate/interviewer projections do not gain this HR field or screening reasons. Retained task/aggregate states are original execution states, not proof a runner is still eligible.

## Export and input

- Existing `GET /api/vacancies/:id/export` stays diagnostic export-all with unchanged columns.
- `GET /api/vacancies/:id/screening-export` includes only undecided applications in a compact decision file: `application_id`, candidate name/frozen account email, submission instant, vacancy title/URL, application URL, concise human-review summary, each non-document answer, each document's authenticated download URL, one result-summary column per configured automated check, separate effective Yes/No/Unknown columns for its predefined skills, then blank `decision` / `reason`. Only the currently supported skill-check type is exported; no speculative question/template outputs are invented.
- Screening export and staff application lists accept optional `processing`, `review`, `from=YYYY-MM-DD`, `before=YYYY-MM-DD`; dates are inclusive-from/exclusive-before UTC midnight. `undecided=true|false` controls staff lists; screening export always forces undecided. Review filters select extraction-bearing records. Candidate requests cannot use these screening/date filters.
- Optional HR-only `readiness=not_required|waiting|blocked|ready|released|locked`, `work` and `recruitmentStatus` use the same SQL predicates as staff lists; these are factual filters, never mandatory review gates. The compact file does not repeat raw processing/readiness metadata. Diagnostic CSV columns stay unchanged.
- Answers use readable choice labels, comma-separated multiple choices and Yes/No, preserving zero/false and distinguishing not-provided/empty choices. Effective result columns use an explicit HR override, including null/unknown, otherwise the machine result. Successful empty skill results are No, not Unknown. Compact result summaries distinguish correction, automated/fixture source and unavailable/pending/failed/closed processing without raw exceptions, task IDs or provenance dumps. Review shows the human editor email when available; no-task review is Not required, never invented approval.
- Export is a repeatable snapshot, capped at 1,000 applications / 10 MiB. Formula-safe quoted CSV, private/no-store. Absolute vacancy/application/document links use the configured web origin, never a request Host or user-supplied redirect. Document URLs are ordinary existing authenticated routes: no public storage paths, signed bearer access, embedded credentials or auth bypass. Sharing the file does not grant access. No export reservation/history marker, automatic decision or new provider call.

Import one UTF-8 comma CSV (optional BOM, LF/CRLF, quoted multiline/escaped quotes). Required unique headers: `application_id`, `candidate_email`, `decision`; optional `reason`. **All other columns, including name/evidence/corrections, are ignored.** ID selects the application inside the vacancy; email must match its frozen submission email after trim/lowercase. Email is an assertion, not an alternate lookup or update. Decision is exactly `preselected` or `rejected` after trimming. Names are not assertions in this version.

```csv
application_id,candidate_email,decision,reason
11111111-1111-4111-8111-111111111111,taylor@example.test,preselected,
22222222-2222-4222-8222-222222222222,riley@example.test,rejected,Optional internal explanation
```

Limits: 1,000 nonblank data records, 10 MiB file, 256 KiB decoded UTF-8 per cell and bounded columns. Upload uses multipart field `file`; invalid UTF-8/quoting/header/missing data is a whole-file error shown in a dialog, retaining previous staging. Bad row widths/IDs/emails/decisions, oversized reason (2,000 characters), missing/foreign application or email mismatch are excluded row errors. Row-width errors preserve the original decision text and explain expected/actual columns; multiple content issues can be shown together. Logical CSV record numbering is not physical line numbering for multiline cells. No expressions execute, silent truncation or identity/answer/extraction updates. Fix malformed content/identity outside the wizard; duplicate selection is handled explicitly as below.

Written screening-rejection reasons are optional and may come from CSV. They are stored only for rejections and never copied into candidate notices. Later recruitment rejection retains its existing required reason/cancellation rules.

The UX-DENSITY-d source [individual screening dialog](interview-api.md#focused-workflow-dialogs--ux-density-d) uses that same shared stage command. Opening or choosing an outcome does not commit; neither outcome is preselected. Confirmation sends the workflow revision; a failure/uncertain response requires explicit refresh and reconfirmation while retaining the local proposal. This changes individual workflow presentation, not CSV/import semantics, first-committed decisions, eligibility or notification rules.

## Preview, confirmation and conflict UX

Staged import rows register with the shared [navigation guard](editor-navigation.md). Leaving the wizard or page while a preview is staged asks Stay or Discard and leave; Hide import and Close wizard use the same explicit choice. A successful apply clears staged rows before any refresh, so it does not prompt. Conflict and uncertain outcomes retain the rows and their guard; the guard never applies, retries or cancels a request.

`POST /api/vacancies/:id/screening/preview`: authenticated multipart upload → `{rows:[{key,applicationId,email,decision,reason,state,issue,issues,parseIssues?,duplicateKeys,candidate,revision}]}`. State is `valid`, `invalid`, or `decided`; `issue` remains a combined/compatibility explanation, `issues` lists individual content/identity errors, optional `parseIssues` names row-structure errors, and `duplicateKeys` identifies repeated source records. Every proposal is checked independently, including duplicates. Candidate identity/revision is returned only after vacancy scope and frozen email match, even if another content field is invalid. Missing/foreign records share an unavailable result. Preview writes no application or notification data.

The wizard has Upload / Review selection / Confirm stages and outcome icons/text plus restrained colour. Invalid identity/proposal rows are barred; CSV-structure errors use a distinct dotted barring; already-decided and deliberately excluded entries are grey. Invalid/decided records remain separately visible and cannot be included. New-tab application links appear only for server-resolved identities; uploaded IDs alone never become trusted links/names.

Valid proposals group by application into one row: all valid CSV record numbers, resolved application link, separate account email and one Screening decision select. Single valid and identical decision+reason proposals default included with the agreed outcome prefilled. Conflicting outcomes start with Select screening decision and are not includable until resolved. Matching outcomes with differing reasons stay prefilled but require an explicit source proposal. Source selection takes its full outcome/reason pair; changing the selected outcome chooses a matching source when unambiguous, otherwise asks for the source reason. An explicit outcome override absent from the source proposals clears the old reason and says so. Exclude application / Exclude all remain available. No proposal is committed by grouping, prefill, inclusion or selection: only final wizard confirmation applies decisions after fresh eligibility review. No silent reason merge, last-row-wins, identity repair or duplicate included IDs; separately invalid/decided rows stay visible/ineligible. CSV literals remain preselected/rejected even though human copy uses Preselect/Not selected.

“Review confirmation” fetches eligibility again while preserving retained proposals/exclusions. New committed decisions are excluded and trigger a warning rather than opening the final confirmation dialog. Failed checks or apply responses require explicit Refresh eligibility; uncertain apply disables editing/confirmation until a successful refresh. Current outcomes are not a causal receipt for an uncertain earlier action. Replacing a staged file goes through the existing Stay/discard guard. Review/extraction updates alone do **not** block screening; only current scope/identity/screening eligibility/workflow revision is checked. No export-time freshness guarantee, reservations, assignment, SSE or Redis coordination.

`POST /api/vacancies/:id/screening/apply` accepts only:

```json
{"rows":[{"applicationId":"11111111-1111-4111-8111-111111111111","email":"taylor@example.test","decision":"preselected","expectedRevision":1}]}
```

Optional `reason` per row. JSON confirmation has a route-specific 10-MiB bound; other JSON routes retain 256 KiB. Empty/duplicate/invalid included sets fail. Server locks vacancy `FOR SHARE`, then applications in deterministic ID order `FOR UPDATE`, validates the entire set before writes, commits each through the shared screening operation, then commits once. Successful result: `{applied,preselected,rejected}`. There is no loop over independently committed HTTP stage calls.

Any stale/decided/invalid included row returns 409 with `{message,conflicts:[{applicationId,state,issue}]}`; **zero changes from this confirmation**. Previously committed decisions by other users stay. Wizard marks conflicts, preserves unaffected choices and requires explicit confirmation of the smaller remaining set. Notification persistence failure rolls back the entire transaction. No automatic partial success, undo or effect replay.

401/403 preserve session/role/Origin behavior; unavailable vacancy 404; input 400; upload/body limits 413. After a network/server failure the outcome may be unknown: wizard disables further confirmation until refresh, does not automatically retry, and never invents a causal receipt from current outcomes. Repeat-import decided records are excluded/conflicts, including repeated identical outcomes.

## Candidate effect and migration

Migration `007_screening_decisions` adds nullable `screening_decision`, `screening_reason`, `screening_by`, `screening_at` to applications and a relational `screening_notifications` table (unique application FK, recipient FK). No backfill invents historical decisions/notifications. No export ledger, votes, claims or assignment tables.

The same screening transaction inserts one generic candidate preselection/rejection notice naming the vacancy, never internal reason/assessments. Candidate Inbox lists/marks read only own screening notices and links to own application; own list/detail now show [coarse public progression/outcomes](application-api.md#candidate-public-status). Staff interview notifications/read-revocation policy remains; candidate roles cannot read old staff interview notifications. Screening rows are retained (no hide/expiry worker); existing seven-day cleanup still concerns old interview notifications only. No process change, email, backfill, submission/appointment/Pass/Offer/Hired notices, owner-finalization alert or full progress timeline is implemented here.
