## Notification policy (clarified C1)

**R2 implemented:** pure staff-only function takes a typed cause/event plus loaded context and returns intents with recipient, interview subject, kind, content and cause. The context map covers every current cause; the switch is exhaustive, including explicit no-effects for current preselection/Offer/Hired. Persistence remains in the command transaction. Reassignment supplies old/new assignee, existing actor copies/deduplication remain unchanged, and the read-side access projection is untouched. See the [current matrix](../current/contracts/interview-api.md#inbox-and-retention); behavioral tests are deferred, not reported passed.

Future effects still need recipient/privacy/channel design; a typed mapping cannot decide importance automatically. Bulk actions need grouping context rather than inferring policy from generic SQL changes.

Separate a policy matrix by recipient relation (actor, candidate, owner, responsible interviewer, future participant) and channel (toast/tray/email/work counter). Return empty effects explicitly where expected. Do not default everyone or every actor to a notification. New candidate/public effects are later behavior changes, not part of a behavior-preserving C1 refactor.

SI already added application-linked screening notifications with scoped reads/deduplication; interview subjects remain supported. Broader receipt/appointment/finalization effects still need recipient/privacy/lifetime decisions, not another implementation of the screening subject. Preserve relational subject ownership and avoid unconstrained polymorphic IDs.

## Revisions and permissions

- R1 extracts existing decisions without merging concurrency into a generic permission gate. `RequireAction` replaces duplicated route-role lists; feature policies are reused at existing mutation checks and advisory projections. Original lock/error/check ordering and recipient-scoped reads remain. Shared response types cover the touched detail/workflow views, not a blanket rewrite of all dynamic/list models.
- Inventory obstacle resolved: typed actions separate legacy canAssess/rescheduling-request from assigned/time-gated feedback; visibility is not authority. Offer metadata uses B1-F's zero-plan/preselected or nonempty/all-Pass rule. Scoped interviewer application access still uses an eligible scheduled/completed assignment on that application; dedicated interview routes preserve the generic-HR-route boundary.
- R3a implements draft PATCH no-ops after owner/editability/stale checks under the existing vacancy lock. It normalizes only submitted stored fields using the same patch schema and deep-compares object content while preserving array order; invalid old selected data does not block a valid repair. The locked read also loads owner metadata so no-op and saved staff projections agree. No new generic revision framework or publish/close-policy change; application tests deferred as Q-R3A.
- R3b compares ordered saved names/instructions before deleting/regenerating IDs, under the vacancy lock and after separate owner/revision/freeze checks. Empty/current-identical drafts do not write; real draft edits retain replace-all behavior. B1-P denies published/closed plan edits even if identical/unscheduled. Real regression remains Q-R3B; focused draft-owner editing/read-only plan inspection is implemented in UI.
- Counters exist for distinct resources; history is not implemented or needed. Remove redundant counter increments only after mapping which commands invalidate which concurrent edits.
- Semantic equality compares normalized editable fields, not IDs/timestamps or raw JSON key order. Interview-plan no-ops now preserve stored IDs; real plan changes still regenerate them. Do not mistake unchanged-save handling for per-entry identity preservation across real edits.
- Check authorization and stale revisions inside the transaction before a no-op return. Selected rule: stale-identical still requires refresh; current-identical does not increment or emit notifications, refresh completion timestamps or discard corrections. Completed review locks corrections; late processing cannot invalidate it.
- Capability names may express `editOwnVacancy`/`readOwnApplication`; resource resolution still happens server-side. Action availability includes state/prerequisites in addition to permission. Shared policy is not a cache that bypasses fresh mutation checks.
- Shared review uses row lock + expected revision and implemented local conflict/refresh/explicit-reapply UX. Exclusive claims introduce expiry/reassignment/abandoned work and remain outside the selected model; do not schedule the completed refresh flow again.
- Most no-op semantics follow from existing business/schema rules: omitted correction leaves an override untouched, explicit null stores unknown, remove clears an existing override (already absent is a no-op); identical saves do not reattribute an editor. Split resource checks for verification, not unrelated constants cleanup. Plan terminology changes do not require renaming internal `stepId`/table/API identities first.
- R3c source checkpoint 2026-11-07: ReviewService validates the whole submitted set, compares normalized skill membership and override presence, and writes only genuine correction/status changes after application-lock/readiness/stale checks. No-op correction submissions do not implicitly start review or initialize tasks; mixed saves preserve unchanged sibling attribution. `review-noop.ts` is a small feature helper, not a generic revision engine. Offline service/race/rollback models and a DOM unchanged-response case do not establish real SQL/HTTP behavior; Q-R3C and all earlier gates remain pending. No migration/data/provider/process operations or UI behavior change.

## Screening, publication and owner finalization

- Screening ignores review readiness; do not add the superseded reviewed-only gate. SI's shared individual/bulk `commitScreening` closes processing and freezes review on either outcome, with transactional claim/start/save/finish and review-write fencing. This guarantee is source-implemented; real PostgreSQL/HTTP race/rollback verification remains Q-SI, not a missing closure implementation.
- Review-readiness projection still matters for optional review: wait for all tasks to settle normally or explicit release; selection freezes unfinished review without completing it. Use factual filters rather than a new “preselection-ready” stage. Exclude frozen review from actionable workload counts.
- B1-P source implemented: VacancyRepository passes a lazy same-transaction plan read into the publication operation while holding the vacancy row lock; publish validates both counters/content. InterviewService save/read policies freeze published/closed plans, even empty/no-op; appointments retain separate permissions. Shared domain schemas prevent divergent authored/stored content bounds.
- Smoke source configures interviews before publish; demo reads the saved plan revision. Initial T2a seed/migrations were applied locally, not a functional smoke or race pass. Isolated models cover serialized publish/edit orders, not actual PostgreSQL races.
- B1-F source implemented: `InterviewService.stage` loads configured/passed counts under the existing vacancy/application locks, then uses shared Offer stage/count policies: empty/preselected or nonempty/interview/all-passed. Workflow action metadata uses the same predicates. Owner authority/revision remain separate; Hired still requires a separate owner Offer → Hired command. No automatic progression or new effects; real DB/HTTP evidence pending.
- Product/UI wording becomes Interviews / Interview plan, not generic steps/pipeline. Keep internal IDs stable unless a separately justified migration is needed; no generic activity engine or post-publication plan mutation.

## Processing and operations

- Current normal parse failures persist terminal/null, but timeouts/storage failures can persist retryable results. Aggregate `completed_with_errors` alone cannot prove a review-ready terminal workload. Stopped service leaves pending; interrupted processing stays processing until expired-lease recovery. Earlier discussion claiming all storage/infrastructure failures leave work open was incorrect.
- Expired-lease recovery currently makes all interrupted tasks retryable, without durable live-admission state. Need a conservative attempt boundary/uncertain outcome policy before continuous execution. Do not test/reset the real spending guard to investigate this.
- New CV-extractor direction adds separate PDF-hash/parser-options Markdown and exact hydrated-request caches, neither implemented. Persist request-level attempt state before sending and coordinate identical requests across workers; an expiring lock/success cache alone cannot resolve unknown paid completion. Gateway reserializes/overrides model, so its effective bytes must agree with hashed request identity. [Integration gaps](research/cv-extraction-lab.md#gaps-the-first-integration-plan-must-resolve).
- B1-R implements shared-HR release of any unfinished work, attribution, durable closure and late-write/review fencing; B1-J/UI provides explicit confirmation and per-field review. No paid restart or false extraction success. Real races/rollback/privacy remain Q-B1R/J.
- SI/release/completion eligibility is enforced at claim/start/pre-execution/save/finish/bind, not only between batches. Preserve transactional fencing when adding task types. External cancellation remains best-effort, not a billing guarantee; uncertain interrupted-live admission is still unresolved.
- `ProcessingService.processOne` invokes executor once per skills task and reuses bytes/text only in local Maps. Selected CV-extractor questions may share one document request; map batch responses back to stable fields and preserve whole-application readiness/closure, response validation and spending guards. No persistent cache/background runner exists merely because the lab handoff describes one.
- CLI can continue other tasks/applications after a returned failure. Terminal task failure does not itself prove a whole batch stops on a gateway block. Define run-level stop behavior separately; gateway blocking must remain a stop condition.
- Runner topology (standalone Nest context, backend child or other bounded process), recovery and shutdown remain open. No queue/BullMQ is required merely because Redis exists. Avoid duplicate runners and automatic draining when API starts.
- Work counts can use cache-aside with short TTL and browser polling; DB remains authoritative. Define stale count indication/error fallback, role/scope cache keys and logout/login reset. No Redis namespace interaction with spending counters.
- File quota accounting spans PostgreSQL and filesystem; a sum-before-write alone races. Retain existing upload caps/compensation; global reservations/reconciliation need an explicit later design, not decorative gateway wrappers.
- No publication timestamp/reference date exists in current vacancy schema/record/snapshot. New publication-relative extraction needs a stored first-publication date under the existing publication lock, explicit timezone/snapshot propagation and a legacy-vacancy policy; creation/last-update time must not masquerade as historical publication.

## Export/import and schema impact

An additive action-policy map or recipient change among existing notification subjects need not change stored shape. Adding candidate notification subjects, hide flags, publication records, participant relations or new decision-cause persistence does.

A new task type does **not inherently require relational tables/columns**: current task type is recovered from frozen definitions and results are JSONB. It does require updated validated contracts, snapshot compatibility and dispatch. Arbitrary result JSON is not enough; validate at input/result boundaries and keep task/output IDs stable.

New enum values require SQL CHECK migration (unless a deliberately reviewed schema replacement is used). Removing `review_ready` need not require removing the stored accepted value immediately; compatibility and data inventory decide. CSV import always needs a contract; new tables depend on provenance/export-history design. Decision reversal has been dropped: editable preview precedes final confirmation. Preview and export tracking are independent; revalidate the included rows at commit, and emit notifications only for committed decisions.

Implemented screening export/import permits undecided applications regardless of extraction/review completion. Compact effective-value decision export is separate from diagnostic export; unknown/failure/provenance stays truthful. Import accepts identity assertions/outcomes/reason, never extraction corrections, and atomically revalidates included scope/identity/workflow revision/state. Review/extraction changes alone are not the selected staleness gate. Grouped duplicates, source reason pairing and final-confirmation-only apply follow the [current screening contract](../current/contracts/screening-api.md); do not reopen settled CSV/atomicity rules as missing design.

`screening-command.ts` owns one transaction for individual/bulk decisions, with deterministic bulk lock order and unique application-scoped screening notice. Migration 007 is applied locally. The related readiness/release and UI work is also implemented; broader notifications and interrupted-live recovery remain separate. Fake-transaction checks are not PostgreSQL evidence.

B1-R derives whole-application readiness from frozen tasks/structured failures, records release actor/time and fences processing. Retry exhaustion/uncertain or unclassified recovery cannot open normal review. Migration 008 is applied locally; B1-J UI/list/export filtering is implemented with partial user-reported release/review evidence. Q-B1R/J integration remainder stays pending. Unsafe uncertain-live recovery still blocks a continuous live runner. Fixtures/disabled AI only; no provider smoke or key changes.

Tests/integration scripts import built `dist/`; rebuild affected packages before trusting a test run. No counted old tests are proof of current behavior after refactoring. Test contracts and invariants, not helper implementation details.

B1-J/R3c/R3d supply explicit release, local draft refresh/reapply, review no-ops and shared dirty/pending guards for review/vacancy/plan/candidate/import. The UI overhaul replaces overlapping primary controls with independent Work to do / Recruitment status, preserving shared server-side list/count/export SQL, original processing/readiness facts and per-field saves. Actual PostgreSQL parity/export/privacy and native behavior remain QA; no automatic merge/retry, screening gate, new counters or provider execution.
