# Requested product changes and decisions

Discussion checkpoint: 2026-11-03. All changes below are unimplemented unless explicitly described as existing. Current baseline: [workflows](../current/workflows.md). R1 was explicitly approved as a refactor of the **old enforced workflow**, not blanket delivery of the selected future rules below. Selected behavior is not implementation authorization; proposed card boundaries/order are in [tasks](tasks.md).

## Readiness, review and progression

**[selected direction, supersedes the mandatory review path]** Extraction/review supports screening; it is not a prerequisite for a screening decision. Shared HR may preselect or reject any undecided application, individually or in bulk, even while processing/review is unfinished. No-task applications need no human extraction review. Do not use “ready for preselection” as a processing/review eligibility gate, including in export/import. Recruitment, processing and review remain separate dimensions, not one linear stage enum.

- Review editing/completion starts for the whole application after all extraction work finishes with success or ordinary terminal failure, or after manual release. Do not introduce a per-task review journey. Answers/files remain viewable before then. A stopped service, interrupted operation or queue/infrastructure problem must not look like completed work; unknown/error values display cleanly.
- Whoever can review can manually release unfinished work into review. Shared admin/recruiter review with conflict protection is selected; no exclusive claim/assignment introduced. Existing revision protection is sufficient in principle; improve conflict/refresh UX. Taking charge of an application remains a possible later discussion, not selected behavior.
- **[selected 2026-11-07]** Manual release may target any unfinished work, including active processing, with explicit confirmation; no detected-stall timer is required. It permanently closes further processing for that application, preserves existing evidence and leaves human review unfinished. Already-admitted external work may still incur cost. [P0-S checkpoint scope](review-processing-contract.md) distinguishes source backend from remaining UI/integration work. Current implementation/checks use fixtures/disabled AI only; no live smoke/paid QA or API-key changes authorized.
- HR may complete review with partial/unavailable values. Forced readiness must not fabricate successful extraction, negatives or human corrections.
- Candidate answers/files remain immutable after submission. HR corrections stay separate and editable during review, then lock at review completion **or either committed screening outcome**, whichever comes first. Screening preserves unfinished review as unfinished; it must not fabricate human completion. Retain existing results/corrections read-only afterwards; they are not a requirement for interviews. No reopening/correction-history UI is planned.
- Processing is not revision-driven: never rerun successful tasks or start extraction after review completion/selection. Manual release or a screening decision closes processing eligibility; fence late saves so they cannot overwrite results/corrections, reopen review or regress recruitment. Eligibility/closure and claim/start/save/finish checks must be transactional, not a frontend check or a check-before-call alone. Cancellation of admitted external work is best-effort, not proof that cost was avoided. Uncertain paid attempts must not automatically retry.
- **[B1-R/B1-J source implemented]** Derive readiness across frozen tasks; persist manual release attribution and structured failure categories separately from retryability. Release/completion/screening fence late writes. UI confirms release; matching list/export filters remain optional facts, not screening gates. Local unsaved corrections survive conflict/refresh for explicit reapplication. [Current contract](../current/contracts/processing-review-api.md#optional-shared-review); migration 008 applied in local demo setup, real integration/manual evidence remains pending. Durable uncertain paid-attempt recovery remains B4-S, not solved by classifying interruption.
- Shared review, manual selection and owner finalization differ: current preselection is shared HR; Offer/Hired owner-only. Do not silently make every decision owner-only.

| Situation | Selected action / effect |
| --- | --- |
| Undecided, extraction pending or review unfinished | HR can preselect/reject; committing either closes processing and freezes extraction/review without marking it complete |
| Undecided, all extraction tasks settled normally or manually released | HR can start shared review; manual release does not decide screening |
| Review completed, still undecided | Corrections locked; HR still chooses preselected/rejected explicitly |
| No extraction tasks | No human review required or attributed; screening immediately actionable |
| Screening committed | No screening reversal/batch undo; preselected applications continue to interviews/owner finalization and may later be rejected through subsequent recruitment actions |

**[requested optimization, not implemented]** Minimize provider requests over shared document text, preferably one request per document where feasible. Current `ProcessingService.processOne` invokes the executor per configured task, with document/text reuse; grouped skills within one task are not cross-task batching. Whole-application review readiness does not require batching first. Design batching separately, preserving task identity, validated results/provenance and all [Jev safeguards](../current/jev-safety.md); no live calls or limit changes authorized.

Assignees belong to application appointments, not interview-plan entries; no publish-time participant requirement is selected.

**[selected; B1-F source implemented]** With configured interviews, all must pass before explicit owner Offer. With zero, preselected is directly eligible for that same owner confirmation. **[later / needs decision]** Archive applications wherever they are when a vacancy closes/is filled. Define close-intake vs finish-recruitment vs archive, visibility, pending jobs and scheduled interviews. Current close only stops submissions; it must not be silently repurposed.

## Notifications, counters and email

**[selected direction]** Separate three UI mechanisms and email:

- Toast: immediate confirmation to the actor. Significant personal events may also warrant a notification, but no automatic actor copy for every action.
- Notification tray: information a person needs for their responsibilities or their own application, avoiding bulk spam. Rename current Inbox terminology where appropriate; icon always present even with zero unread, unread dot independent of workload counts.
- Workload indicators on HR Applications navigation/filters: counts of ready reviews, possibly preselected applications with unscheduled interviews. No per-application ready-for-review tray message.
- Email: independently selected recipients/channel policies. Do not make a notification helper automatically send email too. Existing identity email stays; recruitment emails/external bulk-mail support deferred.

**Candidate direction:** submission receipt notification plus immediate confirmation; preselection notification; interview scheduling/change/cancellation with title, date/time and place/link. A Pass message names the completed interview and says the application continues, not that another appointment is already booked. Rejection communicates the outcome without internal notes. All required interviews passed alerts the owner to finalization availability; for zero interviews, preselection creates that availability. The candidate gets the positive offer message only when the owner records Offer, then the recorded Hired status. Use generic wording appropriate to different contract arrangements, not a promise of a signed contract. Start in-app, mail later; own-application progress supports multiple named interviews and hides internal extraction/review/assessment notes. Current-progress projection versus historical event feed/backfill still needs a bounded contract; do not invent historical events.

For the bounded version prefer rescheduling over standalone appointment cancellation: current cancelled interview instances cannot be replaced for the same configured interview. Avoid standalone cancellation as a normal HR action; rejection still cancels remaining appointments internally and should produce one clear candidate outcome, not several redundant cancellation notices. Shared HR schedules, one responsible interviewer submits immutable final feedback; conflict and overlap checks remain.

**Staff direction:** assignment and scheduling changes notify involved responsible staff; candidate also needs appointment changes. Owner finalization availability is a meaningful responsibility alert, not a default copy of every decision. Exact other feedback/request recipients, initiator inclusion, deduplication/grouping and importance rules need an explicit scenario matrix. Batch actions should not create 100 actor notifications.

**Tray lifetime:** read and hide are separate. User can explicitly hide; no default delete-after-read cleanup in the desired model. Optional per-kind expiry can wait. Hide is not an audit deletion or proof a task is complete. Existing seven-day retention remains operational until a future implementation checkpoint deliberately changes it; no process stop authorized by these docs.

**Work counters:** user accepts browser requests at login and periodic intervals → backend cache-first Redis → on miss query PostgreSQL, repopulate with TTL, return counts. Redis itself does not push to the browser. No WebSocket or counter-maintenance worker selected. **[needs decision]** TTL/poll cadence, HR scope (shared/all vs owned vacancies), count definition for unscheduled interviews, stale-data/error handling. A count plus filter is preferred over another complicated workflow screen. Several interviews can be scheduled ahead. Ready-review workload must exclude screening-frozen applications, not treat unfinished frozen review as an outstanding task.

**Reported gap:** candidate expected a preselection notification after switching roles in the same tab. Current candidate routes/tray do not implement it. Other missed cases are not precisely reproduced; user will retest. Test logout/login cache isolation, links and recipient visibility rather than assuming retention was the cause.

## Export and final selection wizard

[Selected import direction/remainder](screening-import-contract.md) records the later choices. The [source implementation](../current/contracts/screening-api.md) delivers one-CSV export/preview/apply/wizard plus shared screening closure and candidate screening notices; migration 007 applied locally, integration remains pending. This is not delivery of all notification changes in this document.

**[selected direction, supersedes reviewed-only selection export]** Any undecided application can participate regardless of processing/review completion. Unavailable extraction values export blank/null with truthful original status/provenance; HR decides information adequacy. Filters must not become mandatory gates. Exclude already-decided records. Implemented source slice preserves diagnostic export-all and adds explicit undecided screening export; see its current contract for deployment limits.

- Desired filters: dates, previously exported/not exported, search; regex is only a possible request, with syntax/performance unresolved. Externally apply complex language/math rules, spreadsheets, agents or manual selection; no in-platform arbitrary ranking engine.
- Export history/tracking is **deferred**: no accepted batch-ledger or boolean design yet. Define whether downloaded/produced/retried counts as exported and whether it is shared or per HR before schema work.
- **[selected 2026-11-07; source implemented]** One CSV with mandatory application ID, candidate email and `preselected` / `rejected` decision; optional internal rejection `reason`. Other columns, including names/extraction/review, are ignored, never imported as corrections. ID is the application key; frozen email must match. No identity overwrite, JSON or separate outcome-file uploads in the first version. Invalid rows are excluded with reasons, not repaired in the wizard.
- Editable selection wizard: parse rows, highlight problematic ones, and let HR remove invalid rows or manually exclude valid ones. HR can switch proposed rejected rows to preselected and vice versa, individually or using multiselect/bulk buttons. Kanban-like decision groups are an interaction idea, not a drag-and-drop requirement. Excluded rows are unchanged, not rejected. Completely unparseable upload gets a clear error.
- Before final confirmation, show included outcomes, exclusions and unresolved errors clearly; permit further edits or cancellation without persisted decisions/notifications. Invalid rows cannot be forced through by changing their proposed outcome. Candidate identity/answers/review values are never overwritten by the wizard. Missing rows never imply rejection.
- Store rejection cause to distinguish screening rejection from interview-stage rejection. Exact internal stage key/name migration remains open; current key is `not_selected`.
- **[selected direction, supersedes earlier reversal request]** Applied screening decisions are final for individual and bulk/import actions: no manual reversal or batch undo. Flexibility belongs in the pre-commit wizard; notifications to candidates make later undo misleading/complex. Either committed outcome also freezes extraction/review as described above. Preselected applicants continue to interviews/owner finalization; finality means no undo of screening, not stopping later progression/rejection. Bulk rejection must also work for applications whose extraction/review is unfinished, not be hidden behind a reviewed-only export flow.
- **[selected; source implemented]** First committed decision wins; no assignment/holds/debate states. Preview is not concurrency authorization: recheck scope/identity/workflow revision/transitions at apply. Atomic **included set**, not whole original file; conflicts preserve other choices and require reconfirmation, never silent partial apply. Invalid and already-decided rows are visibly distinct. Review/extraction changes alone do not block. New identical decisions on already-decided records conflict/exclude, not replay effects. Unknown outcomes require refresh, no automatic retry/receipt claim. Hierarchy/coordination can be agreed offline; shared HR eligibility does not enforce manager-only authority.

## Action policies and revision design

**[selected direction]** Express what actions can be done and what they require: static role eligibility plus resource/ownership/assignment resolution and state prerequisites, e.g. edit own draft, review shared application, assess assigned interview. “Action policies” is clearer than using “capability” for every requirement. A small Nest decorator/guard plus reusable scoped policy functions/service can cover existing backend and UI actions in a coherent checkpoint; no new permission framework dependency selected. Existing cookie session supplies trusted user ID/role; no JWT migration or stale ownership encoded in a long-lived token.

**[implementation direction]** Coarse guard checks role eligibility; service evaluates record-level authority and prerequisites inside the mutation transaction. API exposes typed action availability/reasons for UI rather than duplicating backend rules; server remains authoritative. Keep business-rule ownership scoped; avoid a global switch growing into every feature's logic. First preserve current behavior, and introduce changed screening/publication rules in their own checkpoints.

Delivered R1 slice: the [current action inventory/contracts](../current/contracts/action-policies.md), shared role eligibility, scoped policies and typed availability across backend/UI. Compatibility fields remain; UI visibility is distinct from authority. This does not implement publication-time freeze, zero-interview Offer, review locks/processing closure or candidate effects. Regression/UX verification is deferred, not passed.

**[selected direction]** Frontend dirty guard + backend no-op detection (`revisionedUpdate` helper direction). Keep small concurrency counters, not historical versions; hide technical counter numbers from normal UI. Under a row lock, check authority/editability and expected counter before comparing normalized editable fields. Current identical saves return unchanged without increment/time/effects/reattribution; stale saves still require refresh even if identical. Actual changes increment once. Omitting a correction leaves an existing override untouched; explicit null stores unknown; removing an existing override is a change even if effective displayed values match (removing an already-absent override is a no-op). Shared HR users see latest editor/save time; preserve unsaved input on conflict for manual reapplication after refresh, with no automatic merging or exclusive claim workflow. Compare interview-plan equality before regenerating stored IDs. UI/backend double validation remains appropriate. Split by resource for verification; derive comparisons from business/schema semantics rather than reopening settled rules.

Delivered slices: R3a backend [draft vacancy PATCH](../current/contracts/vacancy-api.md#staff-createupdate), R3b [interview-plan PUT no-ops](../current/contracts/interview-api.md#interview-plan-saves), R3c [review no-ops](../current/contracts/processing-review-api.md#review-no-op-saves), B1-J local draft refresh/reapply, R3d-a [review navigation guard](../current/contracts/processing-review-api.md#review-navigation-guard) and R3d-b/c vacancy, interview-plan, candidate-application and screening-import guards in the shared [editor navigation contract](../current/contracts/editor-navigation.md). Their real DB/HTTP/manual regression gates remain pending. Authority/editability and expected-revision checks remain separate and precede equality under the mutation lock. Review skill membership compares case-insensitive unordered sets, preserving explicit unknown vs absent overrides; unchanged corrections do not implicitly start review. Same-state publish/close idempotency is unchanged; B1-P independently freezes interview plans at publication.

**[selected 2026-11-07; review, vacancy, plan, candidate and import slices source implemented]** Unsaved-editor leave warnings for review, vacancy drafts, interview plans, candidate applications and screening imports offer Stay or Discard and leave, not a new Save all and leave flow. Current save/submit/apply controls remain explicit; no automatic merge/save/retry/apply. In-app leaving waits for a pending write to settle, without claiming it was cancelled. Reload/tab-close prompts and native-history behavior remain browser-controlled/manual QA. No further entry form is currently unguarded; future editors require their own scoped decision, not blanket authorization from this selection.

## Local mail capture and viewer (later)

Selected simple layout: `mail-outbox/<email-address>/<timestamp>.email`, UTF-8 plain text with `Metadata-Name: value` header lines, a `---` separator, then body. Include recipient, subject and capture timestamp; no HTML/read-state lifecycle. Keep the address recognizable as a safe single directory component. UUID filenames are unnecessary; exclusive creation and advancing to an available timestamp prevents simultaneous capture overwrites. Viewer lists addresses and messages. Current capture still stores only the latest message per hashed address; history/layout change is future work, not implemented by this decision. Recruitment mail remains independent of notifications.
